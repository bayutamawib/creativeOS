# CREATIVE OS — Architecture decisions

CP0 review, 20 November 2026. These decisions specify future behavior. The original database file stopped at the status column of content_items. Its continuation in §4.4 and later sections is a reconstruction from the other specifications. No original tail was available to compare.

| ADR-005 | Workflow B could start planning immediately after strategy. AI §§4–5 and workflow §2.3 require human direction acceptance. ## CP1 foundation decisions

- **ADR-012 · Local service isolation.** Publish the web, API and n8n interfaces on loopback. PostgreSQL is reachable only on the Compose network. Bootstrap a dedicated database owned by the non-superuser creative_app role. The API and worker receive that role’s credential. n8n uses its own persisted editor metadata and receives no application database credential.
- **ADR-013 · Startup and readiness.** A one-shot Alembic service establishes the schema before the API and worker start. Readiness checks the database’s actual revision against the packaged Alembic head. The worker shares the backend image and advances its heartbeat only after that check succeeds. This provides a verifiable lifecycle for the later dispatcher without introducing another queue service.

- **ADR-014 · Browser session boundary.** Next.js forwards same-origin API calls to FastAPI. PostgreSQL stores opaque session and CSRF token digests. Cookies use the __Host- prefix, Secure, Path=/ and SameSite=Lax. The session cookie is HttpOnly. FastAPI requires the configured browser Origin and the session-bound CSRF header on authenticated mutations. Refresh locks the old session and rotates both credentials. Sessions have a 30-minute renewable window and a 12-hour absolute lifetime. A shared PostgreSQL minute counter bounds public authentication attempts across processes.
- **ADR-015 · Privilege transactions.** The agency service acquires the CP0 single-agency transaction lock before rereading actor roles, target roles and surviving active Admins. The client service resolves and locks an owning project and its memberships for grant changes. Composite foreign keys, a partial unique index and a membership invalidation trigger preserve tenant boundaries and grant history. The trigger records the application actor when supplied and the database role for maintenance writes.
- **ADR-016 · CP1 project scope and delivery.** Checkpoint authorization brought minimal project ownership records and project approval grants into CP1-B. Operational project CRUD remains in CP2 and binding decisions on submitted revisions remain in CP4. Authorized inviters receive a single-use invitation link for manual delivery. Reset messages go to an owner-only local development mailbox. The deployed local demo uses generated credentials and separate synthetic organizations.

## CP2 Operations

- **ADR-017 · Client onboarding.** Preserve the CP1 client and project identifiers. Conversion serializes on a lead row. A replay returns the original result. Issuance and redemption use separate client-bound invitation records and the shared CP1 account checks. Existing memberships with a conflicting role require explicit management.
- **ADR-018 · Local event delivery.** The worker claims committed events using expiring PostgreSQL locks and sends a signed, minimal envelope. n8n authenticates the webhook and calls scoped FastAPI endpoints over HTTP. FastAPI authenticates the callback and checks the original signature, timestamp and stored event before recording a run. The development adapter commits recipient-specific inbox rows and the logical step receipt together. The dispatcher requires a matching completed run and response. A lost acknowledgment can start another run without repeating the delivery. n8n operates solely on its own metadata volume.

- **ADR-019 · Project visibility and progress.** Archive projects and preserve their history. New and migrated projects default to draft and medium priority. Historical creator fields may be empty. Project membership is required for Team Member access, and assignment is required to work a task. Managers and Admins control staffing and deadlines. Project and milestone edits serialize on the owning project. The client projection contains status, dates, service type and released milestones. Progress is the rounded percentage of completed milestones in the selected portal's visible set, with zero for an empty set.
- **ADR-020 · Assignment events and task closure.** Composite foreign keys bind each task to its client, project and optional milestone, and each assignee to a member of that project. Removing a project member also removes their task assignments. A new assignment creates one event for its immutable assignment ID. Consumers recheck eligibility before delivery. Closing a task sets its completion timestamp when completed. A manager can reopen a closed task to todo. Team Members can update the status of their own open tasks.
- **ADR-021 · Trigger credentials and execution evidence.** During local verification n8n retained inbound request headers in execution history. The production webhooks now use n8n's built-in HS256 JWT authentication with a 30-second worker token, plus independent timestamped HMAC validation of the event at FastAPI. The old development header value conveys no access to these webhooks. Keep long-lived signing and callback material in environment configuration and n8n's encrypted credential store. Playwright correlates each test's actual resource with PostgreSQL delivery records and independently reads the matching n8n execution's workflow ID and outcome.

## CP3 Creative Intelligence

- **ADR-022 · File storage and brief approval.** Use a private local named volume, opaque UUID storage keys and authenticated attachment downloads. Accept UTF-8 text and decoded, re-encoded PNG/JPEG images up to 5 MiB. Shared brief attachments must belong to the same project. Referenced files retain their bytes when a later brief changes. The database rejects updates and deletes of snapshot rows. The client admin submits, and a scoped agency reviewer decides using the displayed version. A subsequent edit starts a draft and retains the prior approval.

- **ADR-023 · Generation ownership and recovery.** Store the approved input snapshot, approved direction or exact draft revision, resolved parameters, prompt version, model, provider and human or workflow identity with each job. Partition idempotency keys by caller and operation. The existing worker has independent PostgreSQL outbox and generation consumers. A lease token fences completion. Before storing output, recheck project access, input eligibility and revision under the operational and project locks. Transient failures get at most three attempts, invalid structured outputs at most two. Store safe error classifications.
- **ADR-024 · Workflow B and human selection.** The signed brief event runs analysis and strategy through authenticated HTTP callbacks. Selecting a direction emits a separate planning event. The API derives the snapshot and permitted generation stage from the stored event. A delivery retry reuses logical-event jobs. FastAPI computes the terminal state and commits development inbox receipts. Assigned agency users can generate and work on drafts. Admins and Agency Managers make proposal decisions, including selections that create project tasks under the established operational permissions. A selected plan item can become one internal deliverable. Saving copy appends an immutable revision with its generation provenance.
- **ADR-025 · Provider boundaries.** The deterministic fixture and optional HTTPS provider share versioned prompts and strict output schemas. The report interface takes validated metrics and returns a draft narrative. Reporting queries and publication belong to CP5. Local storage is the default for files. The optional Google Drive adapter keeps external object references server-side. Each download uses the recorded provider, an ownership check and a content hash. Operator-supplied Drive access tokens require renewal. Live provider use requires separate credentials and authorization.

## CP4 Content Approval and Operational Automation

- **ADR-026 · Confirmed release.** Assigned Team Members may draft and submit for internal review. Only an active Admin or Agency Manager may request internal changes or confirm approval and release. Project and membership locks serialize review, revision and delegation changes. The approval and client-stage request share a transaction with their audit and outbox event. Client views select released revisions and client-visible feedback. Client sign-off follows ADR-011.

- **ADR-027 · Deadline windows and local deliveries.** n8n calls an authenticated FastAPI schedule endpoint. FastAPI derives the date in the configured agency timezone and records the n8n execution and reminder reservations atomically. Each recipient, task, development channel, reminder type and local date has one durable event ID. Repeated schedule ticks can pick up newly assigned tasks. Delivery checks the current assignment, deadline, task and project status again. n8n uses separate signed webhooks for approval notifications and deadline deliveries. The development inbox records each recipient alongside the logical processing receipt. Client and agency inbox queries recheck access at read time.

- **ADR-028 · Frozen period reports.** Manual project reports accept inclusive local dates. The configurable n8n schedule covers the previous Monday through Sunday for currently planning, in-progress and in-review projects. PostgreSQL captures period completions, due dates and binding decisions, plus current workload, released-milestone progress and client review backlog. A timestamp and metric definition distinguish current state from period activity. Completion counts use the recorded completion timestamp at capture. Reopened work therefore leaves that count. The project lock and period key serialize requests. A database trigger protects metric evidence and published versions. Failed summaries reuse the same evidence in a fresh generation record.
- **ADR-029 · Narrative and export release.** A report job references its project report in place of a brief snapshot. The worker accepts structured AI summaries only when every statement matches a supplied evidence statement or the neutral review recommendation. Human reviewers can edit prose. Each edit invalidates review readiness. Managers and Admins review and publish against an expected version. Assigned agency staff have scoped read access. Client views and on-demand JSON exports share the published-only read query. The same publication transaction writes the audit and outbox event. Draft and publication notifications use the development inbox.

- **ADR-030 · Workflow investigation and replay.** Keep the business event, each n8n workflow attempt, consumer receipt, generation and recipient delivery as distinct records. The manager-only monitoring APIs return identifiers, timing, version, attempt and safe error categories. The local inbox records a successful delivery attempt in the same transaction as the receipt. Historical delivered local notifications supply evidence for their first successful attempt. An expired sending claim becomes uncertain. A replay requires a known transient failure and verified idempotent handling. Explicit retries retain previous attempt numbers and recheck current job inputs. A failed service generation resumes through its originating workflow. Rejected credentials and unclear external send outcomes require investigation. The weekly schedule records each poll timestamp. After ten minutes without a callback the worker marks the schedule attempt failed and leaves the independent summary jobs recoverable. A failed schedule outcome terminates the n8n execution with an error.
- **ADR-031 · Synthetic AI evaluation.** Package ten fictional briefs and six negative controls in an immutable versioned dataset. Each run records its SHA-256, prompt version, fixture provider, model, actual checks and per-case synthetic inputs and outputs. Workflow controls use the real services and a PostgreSQL savepoint for temporary actors, briefs and projects. The runner always selects the fixture adapter. Automated grounding checks compare specific fields with supplied evidence. Managers and Admins can score alignment, usefulness and actionability from 1–5, record grounding and safety findings, and accept or request revision. A failed critical check prevents acceptance. Aggregations count a reviewed output as requiring revision if any current reviewer requests it.

## CP6 Final integration

- **ADR-032 · Execution evidence and credentials.** Disable saving completed, failed, manual and progress payloads in n8n. In n8n 2.48.6, the standard JWT Webhook node authenticates the request and passes its full headers to the trigger output. The execution persistence layer writes that output before any downstream node runs. The built-in sensitive-field redaction applies to output visibility. The supported save switches suppress retained execution history and progress writes while the initial payload still exists. The one-minute hard-delete sweep removes terminal payload rows from normal queries. A privileged reader or backup can capture the transient header before that sweep. Access controls and expiry mitigate that exposure. Keep the original 30-second webhook JWT and scoped, signed FastAPI callbacks. A verifier can match the local n8n terminal event journal by exact workflow ID and execution ID after pruning. PostgreSQL retains the durable run, business event, receipt and recipient records. Access to Docker, n8n metadata and backups is privileged. Pre-CP6 records keep their normal retention.
- **ADR-033 · Read paths and demo isolation.** Load brief associations and released review histories in sets after applying tenant and project scope. Preserve exact revision and feedback projections and reauthorize all mutations in their existing transactions. Server-rendered GETs may retry one transport failure within the original eight-second deadline. Keep fixture checks in both AI-consuming services before running browser journeys. The portfolio test creates its own inquiry, organization and project through the public and protected interfaces. Synthetic captures use a separate Compose project.

- **ADR-034 · Portfolio evidence and provider verification.** Use the isolated, synthetic Compose stack for screenshots and separate the gallery from the single-project browser evidence. Keep credentials, invitation links and raw webhook headers and payloads out of the gallery. Run future live LLM checks only through the documented one-off process, with synthetic data, an approved provider and a bounded request. Keep the demo worker on the fixture.

- **ADR-035 · Controlled Groq verification.** Reuse the HTTPS compatible adapter with the CreativeOS/1.0 User-Agent. CP7 permits one synthetic copywriting request at 4096 tokens and 30 seconds using the durable runner, with the continuous consumers stopped. Persist provider and token provenance, validate the existing schema, retain human release gates and restore fixture mode. Raw generated content is excluded from diagnostic logs.
